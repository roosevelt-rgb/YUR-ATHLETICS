# Franklin mission execution — October 5, 2026

## Owner requirement

Franklin is the personal operating assistant for the whole Desktop. The owner should be able to request an outcome, have Franklin prepare the framework and roles, review consequential actions, and have Franklin carry the mission through its connected tools to verified results. An unavailable phone provider must not be confused with an inability to build an outreach application or campaign framework.

This implementation remains in the existing unified Desktop. It does not incorporate the historical packaging, Port Usher, Switchboard or boot folders. The existing Work OrchestrationManager and Commit Service retain mission/action records. Native IntelliFlow and media execution continue through their established adapters, validation and state owners. No new scheduler, orchestrator, database or cloud resource is introduced.

## Connected operations

Franklin has 55 typed Desktop actions, alongside the existing Work artifact and specialist tools:

- Desktop capability discovery, view navigation and current-state observation.
- Coding runtime discovery; dedicated Franklin session creation; role-labelled task submission; bounded waits and result inspection; cancellation of its own sessions.
- Media catalog, status and job inspection; draft preparation; confirmed generation, resume and cancellation; import and export through the native file pickers.
- Workforce catalog and source-profile inspection; execution and result retrieval for the existing admitted HATCH Quantity capability; reviewed profile assignment into a Franklin-owned coding session.
- Marketplace inventory, pack list and detail inspection; confirmed forge requests, digest-bound manual deployment and native source-pack export through the existing owners. Deployment does not start a run or install donor code.
- Model catalog discovery and integrated browser navigation/reading. Observed visible controls can be clicked, filled or selected after exact native review; short-lived document references and revalidation prevent a changed form from inheriting approval.
- Music catalog, library, draft preparation, composition/lyrics documents, confirmed generation, job status/cancel/resume and export through the existing Music service. The Desktop Music view provides Simple/Custom creation, grouped sound choices and verified audio playback/save.
- Unreal connection status, selected-project inspection and viewport capture through the installed engine MCP interface. Camera changes require a separate exact review. Engine launch, arbitrary scripts and asset mutations are not exposed.
- Optional external Nova site handoff. Nova remains outside Desktop; Unreal has its own Desktop workspace.

The coding tool requires the runtime and workspace observed in the existing Coding selection. Its catalog exposes model identifiers accepted by that connection's existing host resolver and marks compatibility with any active connection. A general Franklin chat model identifier is not interchangeable with a coding identifier. Read-only preflight rejects an incompatible start before showing a human confirmation, and execution checks it again afterward. It does not replace an occupied selection. Franklin owns dedicated coding sessions and cannot submit to or cancel the operator's sessions. Subsequent Franklin turns can inspect or continue its retained sessions in the same app instance. Reconnect invalidates them; persisted Work receipts record the previous outcome, but this version does not restore live session ownership after application restart.

## Mission behavior

Franklin's context instructs it to discover connections, retain a concrete plan and roles using existing committed Work artifacts, submit bounded implementation assignments to IntelliFlow, inspect results and retain remaining work and session/job identities when blocked. The five deterministic built-in specialist contracts are no longer described as the limit of software-building capability.

Tool metadata and Franklin's compiled context specify the coding assignment's exact `session_id`, `text` and optional `role` fields. Media `prompt` and workforce profile `code` are distinguished explicitly. Artifact names must carry the extension for their media type. These instructions address malformed arguments observed during real-model acceptance; they do not broaden execution or confirmation authority.

Work requests without a selected repository omit direct repository-read/proposal tools from their model catalog. Franklin's native Coding workspace is a separate binding; its file operations stay with that worker. Franklin follows actual coding status, readback and commit evidence instead of trying to use an unbound Work file tool. The underlying Work tool permission and path checks are unchanged.

Task submission is not task completion. A runtime response ending is not proof that every requested file, deployment, campaign or external operation succeeded. Franklin receives bounded public output, tool evidence, approval/commit fields and explicit status and must ground its answer in that evidence.

Existing limits remain explicit: 20 Work steps per turn, 10-minute Franklin transport budget, at most 25 seconds per coding wait, and bounded tool arguments/results. A mission that exceeds those limits needs its saved context continued. Closing the window now retains the same running Desktop in the system tray when background operation is enabled. Opening it restores the same window and request context. Explicit Quit shuts down; this does not establish Windows autostart, work during sleep, or autonomous restart recovery.

## Confirmation and recovery

The host shows the exact action payload, mission identity and action fingerprint before consequential execution. The model has no approval-granting action. Native IntelliFlow tool approvals use a separate human decision and recheck current Desktop settings before forwarding it. Imports/exports retain their native path-selection dialogs.

Action identities originate in the existing committed Work step. Mutation identities cannot be replayed after denial, failure or uncertainty. Media and workforce receive request IDs derived from that action identity. Policy and active-window ownership are checked after human confirmation. Scope changes during confirmation prevent dispatch.

Native approval identities are immutable for their connection lifetime. Identical repeated challenges do not create duplicate dialogs; changed scopes invalidate the request; answered challenges cannot be revived. A disconnected or replaced session cannot receive an earlier approval.

- Phone calling, outbound messaging and campaign delivery providers.
- Fresh cloud Music generation: the installed Music service currently reports no configured Suno, Comfy ACE-Step or Eleven Music provider. Existing saved-track playback is independently verified; a provider catalog entry is not a working cloud connection. The legacy Desktop generator remains superseded by the canonical Music service.
- Live Unreal execution: the adapter and native Desktop UI are verified with bounded fixtures and installed engine source contracts, but no live project handshake/capture/camera result has been accepted. Choose an existing running project in Desktop; no candidate project is silently selected or launched.
- Browser actions outside the observed main-frame control contract, including sensitive inputs, cross-origin frames and arbitrary scripts.
- General execution of the Workflows definition catalog.
- Marketplace binary installation, purchase and external publication. Source export and manual deployment use the existing digest-bound review contract.
- Direct donor-code execution of workforce profiles other than the admitted Quantity capability. Other reviewed profiles may specialize a Franklin-owned coding assignment.

Franklin can use the coding harness to develop a missing integration. It cannot claim that its provider is connected or that a live action succeeded without the actual binding and outcome evidence. Existing paid-compute and external-action confirmation requirements remain.
